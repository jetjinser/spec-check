# Goal: contract-vacuity —— 第一条通用 spec 缺陷分析

状态: 进行中（里程碑 ①② 完成，③ 待 vostd 契约清单）
优先级: 高（工具第一条"Verus 不会报"类自动检查）

## 目的

让 spec-check 具备第一类 Verus 自身永远不会报告的缺陷的自动检测能力：
**契约空洞**——契约通过了 Verus 验证，但保证不了任何东西。这是"提高 spec
质量"目标下的第一条插件化分析，也是工具通用性（不绑定特定目标项目）的
第一次验证。

## 缺陷定义（本 goal 覆盖的两类）

1. **前件不可满足**：`requires` 谓词在任何入口状态下都无满足赋值 →
   契约空洞成立。Verus 对此照样报告验证通过。
2. **子句冗余**：某条 `ensures` 子句被其余契约内容（其他子句 + 被调契约）
   蕴含，或从未被任何已注册义务约束 → 该子句是死文本或无证据文本。

## 范围

- 输入：一次成功的捕获目录（VIR + 清单记录），任意项目，不绑定 Vostd。
- 实现：`spec-check-analyses` 中的 `ContractVacuity`，实现 `Analysis` trait，
  通过 CLI 以 `cargo-spec-check analyses run vacuity --capture DIR` 运行。
- 判定标准：以 SMT/验证器层面的**不可满足证据**为准，"assert 失败"本身
  不足以判定（可能是验证器不完备）。

## 阳性 / 阴性对照

- 阳性（必须全部检出）：
  - guard 清单 7 项入口前件恒假（研究档案 contract-scan 已知发现）
  - `TlbModel::tracked_update` 的空洞蕴含（研究档案贡献记录）
  - `MutexGuard::new` external-body stub
- 阴性（必须零误报）：页表 cursor 契约等已知非空洞契约。

## 技术路线（含备选）

- 首选：捕获产物 → 每条契约生成**探针 crate**（对 `requires` 生成
  "存在满足赋值"探针、对 `ensures` 子句生成移除-突变对照），用 verus
  驱动批量判定——与 ktest 通道同一套机制（probe build + replay）。
- 备选：若 VIR 层探针生成成本过高，退化到源级 `#[verus_spec]` 契约探针；
  取舍记录在实现 PR 描述中。
- 风险：探针的不可满足判定需要区分"约束冲突"与"验证器放弃"。首个
  spike 必须先在 1–2 个已知恒假案例上确认判据可行，再铺开。

## 交付物

1. `ContractVacuity` 分析实现 + CLI 接入（`analyses run vacuity`）。
2. 探针生成器与批量判定的确定性重放（沿用 `changed_inputs`/哈希纪律）。
3. 报告：逐契约判定表（判定 / 证据分级 / 复现命令），Confirmed 仅授给
   带阳性对照的探针结果。
4. 测试：合成 fixture 正反例 + 真实捕获上的对照运行归档。
5. 文档：分析配方更新（`ARCHITECTURE.md` 的扩展示例以此分析为范例）。

## 退出条件

- 在 vostd 捕获上全量运行完成，输出逐契约判定表。
- 阳性对照全部检出、阴性对照零误报。
- 第三方可按文档从头重放一次运行并得到相同报告。
- 未产生任何未经探针确认的候选（证据纪律不变）。

## 边界（本 goal 不做）

- 修复建议生成。
- 跨项目批量运行、CI 包装（子命令完成即自然可 CI）。
- 其他缺陷类（test-divergence 等）——但探针生成器的设计应允许复用。

## 里程碑

1. **Spike**：手工在 1–2 个已知恒假案例上构造探针，确认判定判据可行。
2. 探针生成器 + `Analysis` 接线 + CLI。
3. vostd 捕获全量运行 + 阳性/阴性对照报告归档。
4. 文档收尾、第三方重放演练。
