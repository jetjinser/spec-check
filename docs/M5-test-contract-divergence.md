## 1. 分析语义

义务对照（divergence）与 vacuity 互补：

- vacuity 问 **requires 侧**是否空洞（入口前置不可满足 ⇒ 契约对任何调用都成立）；
- divergence 问 **ensures 侧**是否足以支撑使用方义务（client 义务在原契约
  下不可证 ⇒ 契约缺口候选；可证 ⇒ 契约支持）。

代理 client（obligation client）形态（与研究管道一致）：exec fn 以**真实
调用接口**使用目标 API（本地构造接收者 → 调用 → 断言义务），在**原契约**
（目标工作区现有 `#[verus_spec]` 面）下验证。义务 proof 失败且目标工作区
基线自身验证通过 = 契约缺口候选（证明论结论：**契约不足以推出使用方义
务**；不是运行时反例，不证明实现错误）。义务验证通过 = 契约支持该义务。

义务来源（项目侧输入，工具不含任何项目知识）：API 文档描述、相邻 ktest
断言、真实调用点需求。工具只做：注入代理 client → 验证 → span 归因 → 判定。

## 2. Manifest schema（divergence v1）

```jsonc
{
  "target_workspace": { /* 与 vacuity v1.1 完全同构：manifest_path,
                          inject_dir, gate_cfg, extra_cfgs, target */ },
  "contracts": [
    {
      "name": "...",
      "params": "",              // client fn 参数表（通常空：本地构造）
      "obligation": "...",       // 必填：代理 client fn 体（真实调用 + 义务断言）
      "model_preamble": "...",   // 可选：use 导入 / 辅助 spec 源，插在 verus!{ 之后
      "expect": "gap"            // 可选：机器可查预注册（"supported" | "gap"）；
                                 //   运行报告 expect_match，不参与判定
    }
  ]
}
```

义务必须表达在**冻结面现有 spec 面**上（不修改目标源码——契约候选态属
于项目侧独立 checkout，不由本工具制造）。冻结源上不可表达的义务（如
RwLock/SpinLock guard 的 `rel_lock`——该谓词由研究侧补丁引入，冻结面无
此谓词、guard 字段模块私有）不在本分析机械转写范围内，如实记录为边界。

## 3. 探针形态（与 construction 同机制）

注入 `inject_dir/<name>.rs`（`#[cfg(gate_cfg)]`）：

```rust
// Generated by spec-check test-contract-divergence (obligation client probe).
#![allow(dead_code, unused_imports, unused_variables, unused_mut)]
use vstd::prelude::*;

verus! {
<model_preamble>

// ---- obligation client — do not edit ----
pub fn obligation_<i>_<safe>(<params>)
{
<obligation 缩进体>
}

} // verus!
```

两阶段 runner（复用 vacuity construction 回路）：(1) `cargo-verus check
--no-verify` 预编译回路先验编译探针模块；(2) `cargo-verus build` 全量验证
构建，解析日志。注入 replay 副本 + 运行后恢复原字节（InjectionGuard）。
一个 manifest 的全部条目注入同一次构建（基线与义务同一日志，天然对照）。

## 4. 判定规则

日志模型复用 vacuity `parse_target_log`（rustc/verus 诊断 → span 事件，
`Compiling`/`Checking` 分节 + verification results 汇总）。逐条目归因：

- **obligation 区域** = 注入模块内 `pub fn obligation_<i>_<safe>` 的
  fn_region（与 vacuity 同一 fn_region/fn 覆盖约定）；
- **基线** = 目标 crate 内探针模块以外的全部错误事件（冻结源自身契约
  验证必须通过——研究证据形态 "11 pass / client fail" 的机器对应）；
  依赖（vstd 分节）汇总单列。

| 条件 | 判定 |
|------|------|
| 目标分节无 verification results（未验证/中止） | `Inconclusive`（target_not_run） |
| 探针模块内 rustc 编译错误（E05xx 等，`CMarker::Other`） | `Inconclusive`（obligation_compile_error：义务不可表达 ≠ 契约缺口） |
| 基线有错误事件（探针模块外） | `Anomaly`（baseline_verification_failed，人工检视） |
| obligation 区域含 `assertion failed` / `precondition|postcondition not satisfied` 归因事件，且基线净 | `ContractGapCandidate` |
| obligation 区域净，且探针模块净，且基线净 | `ObligationSupported` |
| obligation 区域净但探针模块其他区域有 verus 失败 | `Inconclusive`（harness 不净） |
| 其余组合（义务失败 + 基线败等矛盾形态） | `Anomaly` |

纪律：Inconclusive 不计缺陷；Anomaly 必须人工检视后重分类；
ContractGapCandidate 是"证明论缺口候选"，不含运行时语义；`expect`
不匹配如实报告（expect_match=false），不改写预注册。

## 6. spike 预注册（判据闸门，先于实现写定）

锚点：`mutex-lock-contract`（Mutex::lock 的 guard 引用身份义务；研究证据
原契约 11 pass / client 1 fail，候选（client-injection.patch +
spec-change.patch 依次应用）12 pass / 全量 1496/0）。

义务文本（两面同一义务，表达在两面都可用的冻结面 `get_lock` 上；
`rel_mutex` 引用形态属候选态源码，探针不依赖它）：

```rust
let mutex = Mutex::<u64>::new(5);
let guard = mutex.lock();
assert(MutexGuard::get_lock(&guard) == &mutex);
let _held_guard = guard;
```

模型相对性预注：`==` 在 `&Mutex<T>` 上的语义（引用式或指向值结构式）两
种读法下预测相同——Side A 无任何把 guard 与接收者关联的契约子句（lock 无
verus_spec，MutexGuard 无 type_invariant），不可证；Side B 由 lock 新增
ensures（`ret.rel_mutex(self)`，引用相等语义）+ get_lock ensures（
`guard.rel_mutex(ret)`）直接给出。

| 侧 | 源态 | 预测 |
|----|------|------|
| A（gap 面） | `/tmp/vostd-43da079-ktest-chan`（冻结 + ktest 适配，原样） | `ContractGapCandidate`：义务断言失败归因 obligation fn 区域内；基线净（sync::mutex 自身 11 契约过）；探针模块无编译错误 |
| B（supported 面） | ktest-chan 副本 + client-injection.patch + spec-change.patch | `ObligationSupported`：义务验证过；基线净（研究侧 client 在候选态 12 pass，属基线一部分） |

两面都中 ⇔ 判据验证通过，才进入首站运行。

## 7. 首站运行预注册（vostd 首站，5 条目 / 3 家族）

源：`/tmp/vostd-43da079-ktest-chan`（冻结 rev 43da0797bbfa + ktest 通道
适配；运行后恢复原字节）。义务条目全部机械转写自研究管道已归档义务
（转写规则：义务文本落在冻结面可表达形态上，语义与研究义务一致；
`expect` 依研究结论预注册）。

| # | entry | 家族/模块 | 义务（转写来源） | 预期判定 | 预注册依据 |
|---|-------|-----------|------------------|----------|------------|
| 1 | mutex_lock_guard_identity | sync::mutex（Mutex::lock） | guard 引用身份（get_lock 形态；研究：mutex-lock-contract client） | ContractGapCandidate | 研究 11 pass / client fail；spike A 面同义务 |
| 2 | mutex_try_lock_rel_supported | sync::mutex（Mutex::try_lock） | `ret is Some ⇒ ret->0.rel_mutex(*self)` 字面（契约 ensures 直陈） | ObligationSupported | 义务恰为原 ensures 实例，无推理间隙 |
| 3 | mutex_try_lock_rel_cross_negative | sync::mutex（Mutex::try_lock） | 跨锁义务 `g.rel_mutex(*other)`（阴性对照：ensures 只及接收者，异锁不可证） | ContractGapCandidate | ensures 只给 `*self` 实例；异锁无桥（义务本体为假方向对照，验证判定非平凡 support） |
| 4 | mutex_try_lock_is_none_demand | sync::mutex（Mutex::lock + try_lock） | 持 guard 再 try_lock 得 None（ktest 需求转写；研究：mutex-try-lock-demand） | ContractGapCandidate | 研究 11 pass / 1 error（is_none 断言失败） |
| 5 | rwarc_get_cloned_value | sync::rwarc（RwArc::get_cloned） | `get_cloned` 返回构造值（文档义务；研究：owner-field-return-flows RwArc client） | ContractGapCandidate | 研究 sync::rwarc 8 pass / 1 error；无候选契约（如实记 obligation_fail，不虚构 supported 面） |

预测汇总：**ContractGapCandidate 4 / ObligationSupported 1 / Inconclusive
0 / Anomaly 0**；目标工作区基线净（除探针义务失败外无错误事件）；vstd
2060/0。家族覆盖：Mutex 获取族（#1/#2/#3/#4）+ RwArc 包装族（#5）；
判定方向覆盖：gap 4 + supported 1 + 阴性对照（#3）。

已知边界（预注册）：(a) RwLock/RwMutex/SpinLock guard 身份义务与 RCU
owner 族在冻结面不可机械表达（rel_lock/owner 谓词属研究侧建模态），
本站不覆盖；(b) 义务 fail ≠ 运行时反例，契约缺口是证明论结论；(c)
#5 无候选态两面验证（研究无 adequate candidate），登记 obligation_fail
级证据，不升级 candidate_verified。

## 6a. spike 迭代记录（v1 实测 → v2 重预测；2026-11-11，v2 运行前写定）

**v1 实测**（同一义务文本两面：`let lock_ref = MutexGuard::get_lock(&guard);
assert(lock_ref == &mutex);`）：

- Side A：**ContractGapCandidate**（与预测一致；义务失败归因
  `mutex_lock_guard_identity.rs:17`，基线净 1497 verified / 1 errors，
  vstd 1908/0）。产物 `/tmp/vostd-divergence-spike-a`。
- Side B：**ContractGapCandidate**，与预测（ObligationSupported）**不一致**。
  产物 `/tmp/vostd-divergence-spike-b-run`。根因（运行日志逐字证据）：
  候选态本身验证干净（sync::mutex 12 verified / 0 errors = 11 原契约 +
  研究 client，研究结论复现）；失败的只有我的义务文本。`rel_mutex` 是
  `pub closed spec fn`（两面皆然），client 侧只能作为不透明谓词匹配
  ensures 实例；`lock_ref == &mutex` 需要展开 rel_mutex 体或 get_lock 体，
  两面都推不出——同一文本的转写要求过严，v1 预测的 Side B 半边
  （"由 lock 新增 ensures + get_lock ensures 直接给出"）被运行证伪。

**v2 重预测**（义务 = "guard 保存产生它的锁的引用"；同一语义义务按各态
契约惯用形转写，与研究管道改签名时的做法一致）：

| 侧 | 义务文本（各态惯用形） | 预测 | 判据 |
|----|------------------------|------|------|
| A（冻结原契约） | `assert(guard.rel_mutex(mutex));`（by-value 形，冻结签名） | `ContractGapCandidate` | lock 无任何 ensures，`*guard.mutex == mutex` 无从证出；义务失败归因 obligation fn；基线净 |
| B（候选契约） | `assert(guard.rel_mutex(&mutex));`（引用形 = 研究 client 原文） | `ObligationSupported` | 恰为 lock 新增 ensures `ret.rel_mutex(self)` 的实例匹配（不透明谓词即可）；基线净（研究 client 在列） |

两面都中 ⇔ 判据验证通过。A 面文本是研究义务的 by-value 惯用形
（冻结 rel_mutex 本身就是值比较语义——正是研究发现并修正的建模弱点）；
B 面文本与 mutex-lock-contract client 逐字相同。
